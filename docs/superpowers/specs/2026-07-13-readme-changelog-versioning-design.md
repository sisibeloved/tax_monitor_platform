# README 与 CHANGELOG 阶段版本化设计

## 目标

参考 `sisibeloved/cpython-optimize-skill` 的信息组织方式，在不改变平台运行行为的前提下，让新读者能够从仓库首页快速理解平台解决的问题、四类监测能力、Agent 工作流、验收状态、启动与验证方式，并通过独立的版本历史了解第一至第四阶段交付内容。

## README 信息架构

README 保持中文，并按以下顺序组织：

1. 项目名称、版本与技术状态徽章；
2. 平台定位及当前非生产证据边界；
3. 四类监测能力及预期输出；
4. 月度与季度 Agent 工作流；
5. 代表性验收场景与当前质量指标；
6. 仓库结构；
7. 本地启动、验证、监控、发布、回滚和生产准入；
8. CHANGELOG 入口。

README 只保留使用者与维护者的入口信息，公式细节、架构细节和操作步骤继续链接到现有设计文档与中文手册，避免重复维护。

## CHANGELOG 版本策略

新增根目录 `CHANGELOG.md`，采用 Keep a Changelog 1.1.0 结构和语义化版本号：

- `0.1.0`：季度所得税风险监测基础能力；
- `0.2.0`：业务招待费 Agent；
- `0.3.0`：福利费与公益性捐赠 Agent；
- `0.4.0`：权限、审计、安全导出、模型治理、运维、容量、发布与回滚治理。

四个版本日期依据仓库提交历史记录为 `2026-07-13`。变更内容面向业务使用者和维护者描述显著能力，不逐条复制 Git 提交。顶部保留 `Unreleased`，供后续版本持续维护。

## 一致性与验收

- README 中的公式、阈值、样例结果、测试数量和生产准入状态必须与当前代码及验收制品一致；
- 不宣称真实生产就绪，明确当前证据范围为 `LOCAL_SYNTHETIC`；
- 所有本地 Markdown 链接必须可解析；
- 文档修改后运行 Markdown 链接检查、仓库治理/发布门禁及完整后端、前端验证；
- 合并至 `main` 后再次检查提交关系、工作树状态和关键门禁，再推送 `origin/main`。

## 非目标

- 不改变平台公式、API、数据库、Agent 判断逻辑或部署拓扑；
- 不创建虚构生产批准、真实试点证据或正式发布标签；
- 不删除现有中文设计说明和运行手册。
